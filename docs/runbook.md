# 공통 운영 SOP

주제에 관계없이 재사용할 작업 절차다. 행사별 시각·규칙·제출 형식은 `hackathon.md`, 제품별 결정은 `spec.md`가 기준이다.

## 절차와 결정의 경계

| 공통 절차 | 주제별 결정 |
|---|---|
| 규칙 확인, 역할, 계정 접근, 시간 관리 | 고객·문제·핵심 결과·제품 형태 |
| 리서치·선택·분할·검증·제출 절차 | 언어·프레임워크·라이브러리·폴더 |
| 근거 기록과 완료 판정 방식 | 데이터·저장·인증·AI 필요성 |
| 공식 제출물 체크리스트 | 배포·검증 도구와 실제 실행 명령 |


## 역할

구현·통합 담당은 범위·공유 자원·검증을, 증거·제출 담당은 고객 근거·덱·남은 결선 자리·접수를 관리한다. 인원이 더 있으면 독립 작업·QA를 배정한다. 이름은 context에 기록한다. 에이전트의 역할·모델은 AGENTS와 에이전트 정의를 따른다.

## 단계별 통과 조건

| 단계 | 할 일 | 다음 단계로 갈 증거 |
|---|---|---|
| interview | 미션 원문, 팀 역량·역할, 지급 계정 확인 | context와 mission. 제품 형태·스택은 미선택 |
| ideate | 고객의 실제 작업과 기존 대안 비교, 핵심 결과 선택 | 선택 주제·고객·결과·위험 가정·선택 이유 |
| declare | 새 공개 레포, 주제·아이디어 등록 | 공개 main·선언 완료 확인. 기술 설계는 대기하지 않음 |
| spec | 행동→결과·성공 기준을 먼저 쓰고 필요한 기술 결정 | 제품 범위·실행 계약·소유권·검증 계획 |
| scaffold | 선택한 기술로 최소 실행 환경 마련 | 기록한 명령으로 재현 가능한 초기 실행·접근 확인 |
| dispatch | 가장 작은 입력→결과 경로부터 구현·통합 | 같은 후보의 통합 검증·사용자 시나리오 증거 |
| ship | 선택한 배포 방식으로 심사자가 쓸 URL 확보 | 외부 접근·필요한 계정·실제 결과·유지 담당 확인 |
| pitch | 주장·근거·실제 화면을 공식 형식에 정리 | 현재 제출 후보를 설명하는 PDF |
| submit-check | 사용법만으로 재현, 제출 항목 대조·접수 | 접수 확인·시각·URL·파일·커밋 기록 |

선행 정보가 없으면 그 정보부터 채운다. 기술 선택 전에는 생성기나 설치 명령을 실행하지 않는다. 실행 절차는 선택한 기술의 실제 설정·공식 문서에서 확인한다.

## 제품과 기술을 결정하는 방법

1. **문제:** 어떤 고객이 지금 무엇을 하며, 기존 대안의 어떤 비용·오류가 큰가.
2. **결과:** 심사자가 입력·행동한 뒤 어떤 산출물·상태 변화로 가치를 확인하는가.
3. **제약:** 데이터 접근, 지연, 상태 보존, 권한, 외부 연동, 사용 환경 중 실제로 필요한 것은 무엇인가.
4. **선택:** 팀이 실행 가능한 소수 대안을 구현 시간·위험·배포·검증 난이도로 비교한다. 선택 이유와 포기한 점을 spec에 기록한다.
5. **위험 확인:** 가장 불확실한 경로를 짧게 시험하고, 실패 시 줄일 범위나 대안을 정한다.

인증·저장·AI·화면 수는 필요성을 판단하는 대상이지 기본 필수나 기본 금지가 아니다. 빌드·테스트·실행·배포 명령은 선택 후 cwd와 함께 기록한다.

## 협업 라운드

메인은 plan의 현재 시각 / 남은 시간 / 마지막 검증 후보 / 가장 큰 위험 / 다음 작업을 갱신한다.

작업마다 goal·owned files·done을 지정하고 필요한 입력/출력 계약을 먼저 합의한다. 의존성이 있는 작업은 순서대로, 독립된 작업만 병렬로 진행한다. 파일뿐 아니라 데이터·패키지·검증 출력·서버도 공유 자원이다.

반환된 작업을 통합한 뒤 메인이 실행 계약의 검증을 한 번씩 수행한다. QA는 사용자 행동·예상 결과·실패 복구를 확인한다. 자동 도구가 없으면 사람이 같은 절차를 수행하고 관찰을 남긴다. 검사하지 않은 부분은 미검증으로 둔다.

## 시간 관리 — 이 행사의 팀 운영안

공식 시각은 hackathon이 우선한다. 아래 작업 배분은 조정 가능한 팀 목표다.

| 구간 | 목표 |
|---|---|
| 미션 공개~10:15 | 정보 확인, 고객·결과 선택 |
| 10:15~10:25 | 주제·레포 선언. 공식 10:30 마감 확보 |
| 10:25~11:15 | 요구·기술 선택, 최소 실행 환경, 위험 확인 |
| 11:15~12:00 | 핵심 입력→결과 연결, 덱 초안 병행 |
| 12:00~제출 | 설명 없는 사용 검증, 결함 수정, 배포·PDF·접수 |

권장 제출 목표 13:30. 목표 45분 전 새 기능·새 기술 도입을 멈추고, 20분 전 후보를 확정한다. 늦어지면 부가 범위부터 줄인다. 남은 결선 자리는 라운드 경계와 약 20분마다 확인하며 2석 이하면 즉시 제출 준비도를 점검한다. 이 수치는 공식 규칙이나 통과 확률이 아니다.

## 실패·인수인계

- 같은 오류 2회 또는 10분: 첫 오류·시도·남은 시간을 보고하고 가장 작은 대안으로 좁힌다.
- 핵심 외부 연동·AI 실패: 성공으로 꾸미지 않고 복구 경로와 sample 여부를 표시한다. 핵심 가치가 사라지면 스펙부터 재검토한다.
- 계정·권한·공식 규칙 변경: 사람이 해결할 사항과 진행 가능한 작업을 나눈다. 새로운 비용·외부 조치는 승인 범위 안에서만 수행한다.
- 세션 교체: 새 작업 폴더·remote를 확인하고 AGENTS → context → spec → plan 순서로 재개한다.
- 제출 후: 제출한 버전·URL을 보존하고 공지된 유지 시각까지 담당자가 확인한다. 후속 개선은 별도 후보에서 검증한다.
