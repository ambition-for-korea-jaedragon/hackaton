# /ideate — 10:30 선언을 위한 선택

입력은 `docs/mission.md`, `docs/context.md`. 먼저 `docs/design-refs/judge-perspective.md`와 `docs/runbook.md`를 읽는다. 기본 25분, **10:15까지 선택**을 목표로 한다. 마감이 가까우면 후보·검색 수를 줄여 선언 시간을 확보한다.

후보는 고객·문제·결과로 비교하며 특정 앱 형태·기술 스택을 먼저 정하지 않는다. 필요한 데이터·실행 가능성은 검토하되 기술의 최종 선택은 `/spec`에서 요구를 정한 뒤 한다.

## 근거와 후보

scout 두 개를 병렬로 보낸다. 각각 goal / owned files(읽기 전용) / done을 준다. 5분 내 답, 질문당 최대 4회 검색.
- 고객: 주제에 맞는 구체 직군의 반복 문제와 최근 실제 사례, 원문 링크.
- 대안: 기존 도구·수작업·범용 챗봇이 하는 일, 남는 불편. 공식 가격·기능과 사용자 경험을 구분.

메인은 팀의 도메인 경험과 해외 고객 접근성을 함께 확인한다. 대상 고객에게 물을 수 있으면 최근 실제 작업·기존 해결법·불편한 결과를 짧게 듣는다. 연락은 사람이 하며 인터뷰가 불가능하면 가정으로 남긴다. 팀원의 호평을 고객 수요로 기록하지 않는다.

후보는 **3개**. 표의 열: 선택할 VC 주제 / 고객·국가 / 아픈 순간 / 기존 대안 / 더 나은 한 가지 / 60초 결과 장면 / 가장 위험한 가정 / 첫 고객에게 닿는 경로.

## 선택 기준

먼저 제외: 미션과 안 맞음, 데이터를 구할 수 없음, 60초 데모의 끝 상태가 없음, 첫 동작 버전이 정오까지 불가능함.
남은 후보를 고객 고통의 근거·결과의 가치·팀 경험·구현 불확실성으로 비교한다. 공식 심사 배점처럼 숫자 점수를 만들지 않는다. 시장 크기는 확장 가능성 설명에 쓰고 구현 위험을 덮는 근거로 쓰지 않는다.

추천 1개와 차선 1개, 각 선택의 대가를 짧게 제시한다. 사용자가 선택 권한을 위임했다면 추천안으로 진행한다. 결정이 필요하면 한 라운드로 질문한다. 추가 grilling을 자동으로 이어가지 않는다.
