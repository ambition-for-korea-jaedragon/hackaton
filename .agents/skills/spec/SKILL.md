# /spec — 결과를 먼저, 기술은 그다음

mission/context/ideas/research를 읽고 주제 선언 상태를 확인한다. `docs/spec.md` 양식을 위에서 아래로 채운다. 미션·선택 결과가 없다면 그 단계로 돌아간다.

## 요구와 성공 기준

고객 한 명의 핵심 작업에서 행동·입력 → 결과 → 확인 방법을 정한다. 제품 형태나 화면 수부터 정하지 않는다. 필수 범위와 줄일 순서를 쓰고, 반복 실행·복구·접근 권한을 정의한다.

가치 주장 하나의 비교 조건·측정 방법·한계를 정해 evidence에 기록한다. 주제에 필요한 데이터·도구를 구할 수 있는지 확인한다.

## 기술 결정

결과에 필요한 제약을 근거로 구현·저장·인증·AI·배포 방식을 고른다. 실현 가능한 소수 대안을 팀 역량·구현 시간·위험·외부 접근·검증 난이도로 비교한다. 필요 없는 구성은 이유와 함께 제외한다.

아직 기술을 선택하지 않았다면 여기서 결정한다. 사용자에게 중요한 차이가 있으면 선택을 받고, 위임된 범위에서는 근거와 함께 결정한다. 특정 기술이 익숙하다는 이유만으로 제품 범위를 바꾸지 않는다.

선택한 기술의 실제 설정·공식 문서로 소스 위치, 버전, 설치·실행·검사·배포 절차를 확인해 **실행 계약**에 기록한다. 빌드 없는 도구는 해당 없음과 대체 검증을 적는다. AI를 쓰면 입출력·제한·실패 경로·비밀 관리도 명시한다.

## 계획과 덱

plan에 현재 상태와 작업 표(목표 / 소유 파일 / 의존 작업 / 공유 계약 / 완료 조건 / 증거)를 만든다. 가장 위험한 경로를 짧게 시험한 뒤 가장 작은 입력→결과를 연결한다. 독립된 작업만 병렬화한다.

writer에 goal(공식 두 장의 핵심 주장 초안), owned files(`docs/pitch/deck.md`), done(고객·주제·결과·근거 종류)을 준다. 세부 형식은 `.claude/skills/pitch/SKILL.md`를 읽어 브리프에 포함한다.

완료: 요구에서 기술 선택 이유를 추적할 수 있고, 실행·검증 절차와 작업 소유권이 구체적이다. 다음은 `/scaffold`.
